## 一、轉寫不穩定，靜態別名表救不了

**同一個詞、同一個人、同一支手機、同一場錄音**：

| 技能 | 探測 | T1 | T2 |
|---|---|---|---|
| Angular | Android | **整段消失**（只剩「這個框架」） | Andrew |
| Git | gate | gats | Gate |
| JavaScript | JavaScript ✓ | **加巴screen** | JavaScript ✓ |
| HTML | HTML ✓ | HTML ✓ **與 HDMI 並存於同一段** | HTML ✓ |
| Kotlin | — | Collin | Collin |

`Angular` 三種寫法、`Git` 三種、`JavaScript` 兩次對一次全毀。
`HTML` 甚至在**同一段錄音裡同時出現正確與錯誤兩種形式**。

所以 `stt_confusions.v1.json` 的價值比我昨天以為的低很多。它記錄的是
**已觀察到的變體**，不是映射表——`gate` 加進去了，下次出現的是 `gats`。
只有 `Kotlin→Collin` 這種穩定的才真的有用。

**這條要記進交接文件**：別名補齊這條路對英文技術詞是走不通的，
因為問題不是「有一個固定的錯誤形式」，是「每次都錯得不一樣」。

## 二、填充詞維度不只可用，它的鑑別力很漂亮

用實際逐字稿算（只計詞彙型，非詞彙音已確認會被引擎吃掉）：

| 錄音 | 錄音指示 | 每百字填充詞 |
|---|---|---|
| T3 | 正常發揮 | **3.0** |
| T4 | 多講故事 | **6.4** |
| T6 | **刻意講亂** | **9.8** |

單調、間距明顯、方向完全吻合指示。**這是目前整個模組唯一乾淨的量化訊號**，
你的 subScores 錨點可以放心用。

一個語意上的提醒：`avg_sentence_len` 現在是 69–86 字，那不是「句長」，
是**她停頓前講了多長**（因為段界＝STT 自動送出點）。這其實更有用——
它測的是語流連續性——但 prompt 的措辭不要講成「句子長度」。

`segmentation` 三格都回 `punctuation`，因為多段用換行接。**段界變成句界，
`sentence_count` 從估算值變成實測值**，這是分段送出白撿的好處。

## 這對設計的含意：偵測應該以履歷為條件，不是掃全表

現在的作法是拿 110 條詞彙表去掃逐字稿。但我們真正要回答的問題很窄：
**「這個人履歷上的這 8 個技能，他討論到哪些？」**

差別很大。掃全表時「加巴screen」什麼都不是；但如果我知道**這份履歷有
JavaScript**，那「加巴screen」就是很強的候選——`加巴` 的發音接近 `java`。
同理 `Andrew`←`Angular`、`ajex`←`AJAX`、`ASP點net`←`ASP.NET`、`gats`←`Git`。

而不對稱性支持放寬：使用者講了卻被說沒講 → 假指控，當場失去信任；
其實沒講卻被算成講了 → 少一條建議。所以**對履歷上已有的技能，
應該用寬鬆的匹配器**，範圍限縮在那 8 個詞，誤傷面積很小。

我打算 W2 做這件事（模糊／注音匹配，只對履歷技能開），
它比補別名有用得多，因為它不需要預先知道會錯成什麼。

**這也修正了我先前跟你說的「W2 重心往補別名挪」——那個建議在這份資料前失效了。**
補別名對付得了穩定的錯誤，對付不了每次不同的錯誤。

## 你那側可能想知道的三件

**一、T6 的 PowerPoint 是講者沒講，不是轉錯。** 這正是「要點卡 ≠ said」的實例——
標記必須讀逐字稿，不能照錄音指示填。我們標的時候會照實標成 `said=0`。

**二、語意破壞在中文也有，只是不影響技能偵測。**
`deadline→daylight`、`分工→分公`、`攝影社→剩一色`、`社課→射刻`、`打工→打エ`。
技能詞沒事，但你的 `starParts` 要從這種句子裡抽 STAR 結構會很吃力。
T3 那句「給他設定一個 daylight」其實是「設定一個 deadline」——
那是專案時間控管的關鍵證據，但字面上讀不出來。

**三、單一講者。** 六段都是同一個人錄的，所以口音／咬字這個維度上是 n=1。
英文詞 36% 這個數字要理解成「這個講者在這支手機上」，換人可能不同。
不影響我們用它做校準，但寫進報告時要標明。
