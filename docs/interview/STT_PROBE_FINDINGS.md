# STT 探測結果與設計變更（A → B）

實測資料到手（Galaxy S24 / Android 16 / Google App 17.44.15）。
它推翻了我一個核心假設，修正了測試者的一個結論，並暴露一個比兩者都嚴重的失效模式。
程式已改完，42 passed。

---

## 一、我的 `kind` 判準方向是反的

把 23 句的轉寫結果餵進實際管線，量「這個技能詞抓不抓得到」：

```
英文 / ASCII 技能詞    抓到 15/25  (60%)
中文技能詞            抓到  7/9   (78%)
```

我原本的判準是「ASCII → hard（可靠）、中文抽象詞 → soft（濾掉）」。**反了。**

具體看：被我判成可靠而放行的 `Angular` `Git` `jQuery` `AJAX` `MS SQL` `ASP.NET`
`Google Analytics` 全滅；被我判成不可靠而濾掉的 `專案時間╱進度控管` `帳務處理`
實測都完美存活。

原因回頭看很清楚：**中文詞是模型的母語，英文專有名詞是外來詞**，
zh-TW 辨識對後者本來就弱。我當初用「是不是專有名詞」推「會不會被講出來」，
但真正的變數在轉寫端不在說話端。

**已改**：`kind` 不再從字串推導，改查 `MEASURED_KIND` 實測表，
查不到才落回啟發式。這正是我 D1 說的「W2 用實測值取代」，只是提早發生了。

## 二、修正測試者的結論：填充詞是**部分**移除，維度沒死

回報寫「13 處填充詞全部消失，建議重新設計該評分維度」。逐詞比對後不是這樣：

| 填充詞 | 原稿 | 轉寫後 |
|---|---|---|
| 嗯 | 5 | **0** |
| 呃 | 5 | **0** |
| 那個 | 2 | 2 |
| 就是 | 7 | **8** |
| 然後 | 1 | **3** |

非詞彙填充音全數移除（有兩處被轉成「而」）；**詞彙型填充詞完整保留，
甚至因斷詞而超計。**

這正是我上一則預測的部分抑制。所以結論不是「維度要重新設計」，而是
**維度變窄了**——測得到詞彙型，測不到非詞彙音。而詞彙型本身就是有效訊號：
每句都講「就是」的人確實不流暢。

**已改**：`FILLERS` 縮減為只含詞彙型。這讓 `filler_count` 變成對它自己的定義
而言完整的測量，`filler_reliability` 回 `measured`。**合約不用加第五個值**——
改變的是「測什麼」，不是「測得準不準」。

你的 prompt 唯一要注意的是：**不要宣稱它涵蓋全部口語習慣**，
它涵蓋的是詞彙型填充詞。

（`嗯/呃` 我保留在 `NON_LEXICAL_FILLERS` 但不計數。它們現在有兩個用途：
若哪天出現了，代表換了裝置或引擎，是引擎變更的偵測器；打字輸入時它們會出現。）

## 三、真正嚴重的是這個：STT 會把技能轉成**另一個真實技能**

不是諧音走樣，是替換成另一個存在的東西：

```
Angular            → Android
Google Analytics   → Google Maps
鼎新                → 頂新
```

這比「抓不到」嚴重一級，因為它產生**雙重錯誤**：使用者講了 Angular，
系統認為他沒講 Angular（假指控），同時認為他講了 Android（憑空記上一筆）。

而且不能用加別名解決——`Android` 本身是常見技能，把它設成 Angular 的別名，
真正的 Android 就永遠抓不到了。

**已改**：別名分兩類處理。

`data/stt_confusions.v1.json`：

- **safe_aliases**（轉寫形不是任何真實技能）→ 直接進詞彙表
  `gate→Git`、`Jerry→jQuery`、`a-x→AJAX`、`msc庫→MS SQL`、`ASP打net→ASP.NET`、
  `C Sharp→C#`、`View JS→VueJS`、`react JS→ReactJS`、`報表會診→報表彙整與管理`

- **colliding_aliases**（轉寫形本身是真實技能）→ **履歷條件判定**
  只在「履歷有 Angular 且沒有 Android」時，才把 Android 的命中補記為 Angular。

條件判定的正當性還是那條不對稱：使用者講了 Angular 卻被說沒講 → 當場失去信任；
使用者其實講 Android 卻被算成 Angular → 少一條建議。取代價小的。
而且條件把誤判限縮在「履歷本來就有那個技能」的窄範圍內。

★ **`C Sharp→C#` 這條特別值錢**：那不是辨識錯誤，那是 C# 的**口語形**。
人講「C Sharp」，STT 忠實地寫下來。這類條目應該長期留在詞彙表裡，
跟裝置無關。

## 四、兩個影響輸入形狀的引擎行為

**停頓 1–2 秒就自動送出。** 長回答必然被切成多段——實測者錄兩分鐘自我介紹
就得拆四段。所以 `transcript` 在正式環境本來就是**多段而非單一字串**。

好消息是這對我有利：黃金集的 `transcript` 欄位我改成 `transcript_segments`
（字串陣列），下游用 `"\n".join(...)` 餵給 `compute()`。換行本來就是我的斷句符號，
所以 **STT 的送出邊界直接變成句界，`sentence_count` 從估算值變成實測值**，
`segmentation` 可以回 `punctuation`。白撿的。

**你那側要確認的**：`InterviewSession.turns` 怎麼壓成 `transcript: str`。
若是直接串接無分隔，那個邊界資訊就丟了。建議用換行接，合約不用改。

**語意反轉。**「蠻有興趣」→「沒有興趣」，兩次獨立測試都出現，非偶發。

這個我沒有解法，但它必須被記下來，因為**它是這個產品最危險的失效模式**：
評分會針對使用者沒說過的話。漏講判定受影響有限（它看技能詞不看情態），
但你的 `starParts`、`questionFeedbacks`、`subScores` 是直接讀語意的——
一句反轉的話會讓回饋整段錯，而且錯得很有說服力。

值得在 UI 上考慮一件事：**讓使用者看得到自己的逐字稿。** 他一眼就能發現
「我明明說蠻有興趣」。這比我們在後端做任何補救都有效，而且成本只是多一個畫面。
這是你和怡君的決定，我只負責把風險講清楚。

## 五、n=1，這張表不是定論

同一句兩次測試結果不一致（「四年級」→「大事」、「怡君」→「李宜君」，
第二次又正確了）。代表**部分詞彙轉寫不穩定**，單次觀察不足以判定。

所以 `stt_confusions.v1.json` 不是確定的映射表，是**已知會發生的變體清單**。
它讓管線多認得幾種寫法，不保證涵蓋。這一點寫在檔案的 `_caveat` 裡了。

不穩定本身也是設計含意：**穩定的別名補得完，不穩定的補不完。**
所以長期不能只靠表面掃描，語意段仍然要做——但它的角色從「處理軟技能」
變成「處理轉寫變異」，這是探測改變的第三件事。
