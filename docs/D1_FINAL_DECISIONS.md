## 修正：STT 沒有引擎可選，你的前提要改

你問 faster-whisper 在 Windows + Python 3.13 裝不裝得起來。**不要裝，這是白工。**

我核對了前端原始碼：

```kotlin
// ui/components/InPageVoice.kt
import android.speech.SpeechRecognizer
SpeechRecognizer.createSpeechRecognizer(context)
val voice = rememberInPageVoice(languageTag = "zh-TW") { transcript -> submitAnswer(transcript) }
```

全 repo 沒有任何 whisper、speechmatics、音訊上傳、`MediaRecorder` 的跡象。
三個 live 頁全部走 `rememberInPageVoice`。

**STT 是 Android 裝置端的 `SpeechRecognizer`，音訊不出手機，後端永遠只收到文字。**
引擎已經定了，沒有選擇題。我們也裝不起來——那是 Android 系統 API，不是 Python 套件。

### 但你的擔憂本身完全正確，只是解法不同

你說「黃金集會把引擎特性烤進參數」——對。而且更麻煩的是：
**黃金集的逐字稿不能用錄音產生。**

黃金集要求 `expected_missing` 精確，也就是要知道使用者**確切漏講了哪 N 個亮點**。
真人錄音的內容不受控，講出來的東西無法預先決定，答案卡就不成立。
所以逐字稿必須是構造的，這是這份測試集的前提，不是偷懶。

於是真實樣本的角色不是資料來源，是**格式規格**：

| 要從樣本讀出的特性 | 影響 |
|---|---|
| 標點:預期完全沒有 | 你的斷句、我的 `starParts` 引用 |
| 數字怎麼呈現(阿拉伯數字或國字) | 你的量化詞偵測 |
| 英文專有名詞怎麼寫(SQL / sql / 艾斯扣). | **你的表面掃描命中率，這條最關鍵** |
| 填充詞會不會被吃掉 | 我的 `text_stats` 錨點 |
| 中英夾雜的空格處理 | 兩邊的斷詞 |

第三條對你影響最大：如果 Android STT 把 SQL 轉寫成「艾斯扣」或「Sql」，
你的表面掃描會全滅，而那正是你剛用詞頭匹配救回來的那一層。

### 所以我要跟怡君要的東西改了

不只是「一段樣本」，而是**一份格式清單**：她錄三段刻意涵蓋硬技能英文詞、
數字、填充詞的回答，把 `InterviewSession.turns` 原樣貼出來。
