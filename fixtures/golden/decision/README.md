# 決策放行條件的量測用答案階梯

`answers_v1.json`。兩支工具共用:

    tools/followup_rate.py    三種難度的追問率
    tools/star_read_eval.py   STAR 事實判讀的準確率

## 這不是一般的 golden set

`fixtures/golden/interview/` 是技能漏講的標註集,一筆一個案例,彼此獨立。
這裡是**一個量尺**:同一個專案的七種講法,完整度由低到高排,
每一階剛好跨過 `AcceptRule` 的一條門檻。

拆開單獨看任何一筆都沒有意義,要整組一起跑。

## 標註是什麼

| 欄位 | 意思 | 對應的放行條件 |
| --- | --- | --- |
| `star_parts` | 這段話交代了 STAR 哪幾段 | `min_star_parts`、`require_result` |
| `quantified` | 成果有沒有可查證的數字 | `require_quantification` |
| `tradeoff` | 有沒有交代放棄了什麼、依據是什麼 | `require_tradeoff` |

**標註只記這段話裡有什麼,不記期望的動作。** 期望動作由
`tools/followup_rate.py` 從 `AcceptRule` 算出來。

這件事很重要:放行條件已經有兩種表現形式——
`render_accept_rule()` 把它變成 prompt 文字,`accepts()` 把它變成判斷。
如果這份檔案再手寫一份「A3 在中等應該被追問」,那就是第三份,
改了 dataclass 之後三份一定會漂,而漂掉的那一刻量測結果會變成錯的但還是綠的。

## 階梯是怎麼排的

| | 段數 | 結果 | 數字 | 取捨 | 新手 | 中等 | 困難 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A1 | 1 | ✗ | ✗ | ✗ | 追問 | 追問 | 追問 |
| A2 | 2 | ✗ | ✗ | ✗ | 放行 | 追問 | 追問 |
| A3 | 3 | ✓ | ✗ | ✗ | 放行 | 追問 | 追問 |
| A4 | 3 | ✓ | ✓ | ✗ | 放行 | 放行 | 追問 |
| A5 | 4 | ✓ | ✓ | ✓ | 放行 | 放行 | 放行 |
| A6 | 4 | ✓ | ✓ | ✗ | 放行 | 放行 | 追問 |
| A7 | 3 | ✓ | ✓ | ✓ | 放行 | 放行 | 追問 |

右邊三欄是算出來的,不是標的,列在這裡只為了讓人看出階梯有沒有排對。

每一條門檻都至少有一筆跨過它:

    A1 / A2  段數下限(新手的 2 段)
    A2 / A3  結果段(中等開始要求)
    A3 / A4  量化(中等開始要求)
    A5 / A6  取捨(困難才要求)
    A5 / A7  任務段(困難的 4 段)

A4 在困難同時少了段數跟取捨,所以 A6 必須存在——
不然困難追問 A4 時分不出是哪一條在作用。

## A7 是為了讓「任務」這一項可以被驗,而且驗出了東西

`tools/star_read_eval.py` 量 STAR 事實判讀的準確率,而判讀錯了不一定改變放行判斷。
第一輪實測六項裡五項滿分,只有任務那一項壞(0.29–0.70),判斷一致率卻照樣接近
滿分——因為 A2、A3、A4 的任務判錯都不會跨過任何門檻。

A7 是 A5 去掉任務那一句:三段,而結果、量化、取捨全滿足。
困難要四段,所以**任務在不在單獨決定困難要不要追問**:

    標準        3 段 → 追問
    T 誤判成有   4 段加三個條件全滿足 → 放行

A1 在新手是另一個同樣性質的格子(1 段,T 誤判成有就變 2 段剛好過門檻),
但那一筆結構單薄;A7 是完整的回答,只少一句話。

**它抓到的東西**:句子分派把任務從 0.29 推到 0.86,只剩 A7 失敗,而且 5/5
都把取捨那一句掛成 T——「我判斷兩個月的時間只夠做一件事」讀起來就是一個目標。
同一份記錄裡,單題呼叫對同一句話的判讀是「取捨」而且正確。

所以問題不是模型讀不懂,是**分派的標籤集合裡沒有取捨的位置**,
那句話只能掛「其他」,而垃圾桶比不過看起來很貼的 T。
加一個「取捨」標籤之後任務是 1.00。

這一輪沒有 A7 就會停在 0.86 而且不知道為什麼——A2、A3、A4 的誤判不改變判斷,
而那三筆的誤判原因跟 A7 完全不同。

## 這組標註也是事實判讀的標準答案

`star_read_eval.py` 直接拿 `star_parts`、`quantified`、`tradeoff` 當 ground truth,
一項一項算準確率。那組標註本來是給追問率當量尺的,不是為判讀標的——
能共用是因為兩邊問的是同一件事:**這段話裡有什麼**。

目前的實測(5 回合 × 7 筆 = 210 次判讀,句子分派加兩次單題):

| 情境 | 任務 | 行動 | 結果 | 量化 | 取捨 |
| --- | --- | --- | --- | --- | --- |
| 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |

把這些事實餵進 `accepts()` 推出來的追問率是 0.143 / 0.429 / 0.857,
跟標註算出來的期望值完全相同。

加答案會讓那三個期望值改變(它們是從標註算的不是寫死的),所以加完要重跑兩支工具。

## 刻意避開的東西

`forced_decision()` 會在四種情況直接決定、不呼叫模型:
空回答、`ended_by="timeout"`、追到深度上限、明確說答不出來。

這七筆每一筆都不能命中前三種,而且不含
`_ADMITS_UNKNOWN`(不知道 / 不確定 / 沒想過 / 沒有經驗 / 答不出 / 不太清楚)
任何一個字串,否則量到的是程式的決定而不是模型的判斷。
工具啟動時會檢查這件事。

## 為什麼有標點

`meta.engine` 是 `api`。雲端轉錄不漏字、有標點,`CLARIFY_BY_ENGINE["api"]`
的判準也是照這個寫的。要量 `device` 引擎時由工具去掉標點,
不另外存一份——同一組答案存兩份就會變成要同步兩份。

## 加答案的時候

照階梯的邏輯加:新的一筆要能單獨隔離出某一條門檻。
再加一筆「四段齊全有數字有取捨」沒有任何量測價值,只是讓分母變大。
## 自述困難另有一份

`answers_struggle_v1.json` 量第七項事實 `struggle`,不放進上面這組階梯。
階梯是追問率的量尺,測試裡寫死 0.143 / 0.429 / 0.857,加答案會改掉這三個數字。

六筆共用 A6 的本文,只換最後一句:三筆正例(直接認錯、軟性說卡住、
外部原因加自己那一份),三筆反例(只有外部困難、只講成就、明講沒有困難)。
後三筆是難例,窄定義有沒有守住看它們。

    python tools/star_read_eval.py --answers fixtures/golden/decision/answers_struggle_v1.json

`answers_v1.json` 的七筆沒有 `struggle` 欄位,不計分。
