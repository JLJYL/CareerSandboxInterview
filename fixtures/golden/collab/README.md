# 群面協作切片黃金案例

`CollabObserver.observe()` 的回歸案例。跟 `fixtures/golden/interview/`
(漏講點那組)分開放,因為兩者測的東西不同:那組測「有沒有講到某個技能」,
這組測「多方對話被切成什麼形狀」。

## 這組案例測什麼、不測什麼

**測(確定性、現在就能驗)**

切片的形狀。同一段多方對話進去,四個維度各自應該產出幾則切片、
每則長什麼樣、配對配給誰。這部分完全由 `collab.py` 的規則決定,
不涉及語意判斷,所以可以寫成斷言鎖住。

**不測(需要真實資料 + 人工標記)**

BARS 等第。切片正確不代表評分正確——「這段發言算 level 3 還是 4」
是語意判斷,由 B 的 LLM 做,而驗證它需要人工標記的真實對話。
每個案例都留了 `bars_labels: null`,真實資料到位、有人標了之後再填。

**★ 合成資料只能驗形狀,不能驗語意。**
拿合成對話去「驗證」LLM 評分會得到一個看起來有在測、實際上在測
自己編出來的預期的東西——那比沒有測試糟,因為它給人已經驗過的錯覺。

## 資料來源標記

`meta.source` 有兩個值:

    synthetic   人工編寫的對話,只用來鎖切片形狀
    real        真實錄音轉錄 + 人工標記,可以用來驗語意

目前全部是 `synthetic`。等怡君的 Whisper 樣本 + 真實群面資料到位,
新增的案例標 `real`,並補上 `bars_labels`。

## 已知限制:主考官與 AI 同儕無法區分

`UtteranceDTO` 只有 `speaker`(顯示名稱)、`content`、`is_user`,
沒有欄位能分辨「主考官」與「AI 應徵者」。而 `speaker` 合約明文
警告不可用於判斷身分(persona 顯示名稱會隨調校變動)。

後果(見 `case-05`):

    傾聽與回應   使用者的開場會被配對成「回應主考官宣布題目」。
                 主考官不是在提論點,拿 BARS 評「有沒有指涉前一位
                 的具體內容並做加法」,開場發言會被系統性評低——
                 那不是傾聽失敗,那是開場。

    參與主動性   使用者第一則被標「接續他人之後」,但在討論的意義上
                 他是第一個開口的參與者,行為上是起頭不是接續。

`case-05` 把這個結構固定下來,並在 `expected.known_issue` 標明
目前的行為是「已知不理想但符合現行規則」。欄位補上之後,
這一格的預期值要跟著改,而測試會強迫這件事被看見。
